## Why the fix closes the reported defect

The creator derives its receipt from the generated value, exact written bytes
and open file/directory descriptors. It never decides what it generated by
rereading the destination pathname after an asynchronous boundary. The receipt
is written exclusively and fsynced before returning to the adapter.

The adapter retains that identity before its next phase or listener await,
compares the current owner key before binding and again before service start,
and detects creation-receipt changes. Post-start verification binds the creation
receipt, binding receipt and current owner key. Existing one-use and absent-key
guards reject interrupted/ambiguous attempts instead of adopting, deleting or
rotating an unexpected key.

Source review covered the creator, cutover adapter, key-state checks, preflight
change, helper inclusion and fault fixtures against `8b395de`. The four runtime
helper changes match the declared allowlist; app80843c0, source target00f9e197,
