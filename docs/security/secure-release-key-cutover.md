# R5 owner-key exposure boundary — implementation contract

APP80843c0 and SOURCE00f9e197 remain fixed; R1–R4 remain required. No production
key may exist while the BASE root gateway (fileRoots `/`) is running. Mode0700/
0600 and new file roots do not protect a key from that old process.

Chosen flow: retain the exact sealed old watcher's authenticated dual ALL-idle
checks. Its invocation gets a sealed, invocation-local `systemctl` adapter in PATH,
which accepts only `restart codex-remote.service`; it calls the real systemctl by
absolute path. The adapter verifies the bound cutover permit, receipt age/content,
exact installed app/config/dependencies, and key absence; stops the service;
proves old PID/start identity gone, unit inactive/MainPID0, old service cgroup
empty and loopback listener closed; only then runs the existing sealed init CLI.
It binds nonsecret key identity durably, rechecks boundary/config and starts the
new required gateway. No other command is forwarded. No service unit/ExecStart
change or general-purpose systemctl replacement. No key generated by preparation.

Preflight uses structural configuration/provision readiness plus sealed absence
of the final key and prior binding; no reusable secret is generated/read there.
The runner binds the actual generated key receipt before using the new encrypted
adapter. Existing/unbound keys block first activation and are never reused or
silently rotated. Normal restarts use the native systemctl path and the existing
key; provisioning is only for this one cutover permit.

An explicitly stopped systemd service does not auto-restart on Restart=on-failure.
Verify effective KillMode=control-group, SendSIGKILL=yes and no socket activation
before relying on stop. The runner does not restore old modules/env after failure.
A crash before stop leaves key absent; after stop may leave absent or a new key,
but the old process/cgroup/listener must already be gone. After key generation,
only exact installed required-mode code is eligible for start. Failure/unknown
start outcomes retain cutover phase/PID/key-binding receipts and need operator
review, never automatic replay or rotation. A surviving old keepalive/upgraded
connection is terminated by the proven process boundary, not merely Nginx reload.

The contract is cooperative against unintended drift, not protection against
root executing another old gateway manually. The parent runner must be alive and
hold the shared deployment lock at each new effect. The adapter cannot fabricate
approval/profile evidence or extend the one-hour execution readiness lifetime.
Tests must use actual old/new fixture processes and this adapter, including crash
windows, key absence/read denial, retained key on normal restart, and safe failure.

The service-stop assumptions follow systemd's upstream documentation:
[Restart/explicit stop](https://raw.githubusercontent.com/systemd/systemd/v252/man/systemd.service.xml)
and [control-group termination](https://raw.githubusercontent.com/systemd/systemd/v252/man/systemd.kill.xml).
The actual adapter checks the effective policy and independently checks process,
recursive cgroup and TCP boundary; service-control success alone is insufficient.

Fixture I/O substitutes only service manager/source lookup with owned processes;
the real cutover adapter, receipt/destination/config guards, isolated TCP probe,
key CLI, key-binding fsync and phase journal execute. Legacy HTTP uses the exact
BASE compiled module verified by hash; new HTTP uses exact APP and fake native RPC.
Held keepalive/upgraded sockets die with the old process. New encrypted CLI works
and ordinary restart keeps the same key. No host service is stopped by these tests.

Acceptance: 80/80 focused controls (59 prior +21 R5), old/new CLI lifecycle and lint
pass with one worker. New negative controls include configuration drift during
socket-probe awaits before generation/start, key removal/rotation, failed stop/start,
remaining cgroup members, one-use retry rejection and an actual executable adapter
rejecting unrelated systemctl commands. SIGKILL and SIGTERM leave durable phase
state with unknown effect status; they never authorize automatic replay.

The original watcher's 40-second service-call timeout remains. A slow/failed
cutover may leave the service stopped or an unknown new-start outcome; inspect
receipts before recovery. No timeout or missing evidence authorizes plaintext
fallback, old-code restore, implicit key adoption or rotation. These fixture
results do not constitute independent acceptance of this new runner or a live
production deployment. Nginx/app/dependency bytes are unchanged from the accepted
payload; reuse hashes/evidence rather than rebuilding or rerunning Nginx needlessly.
