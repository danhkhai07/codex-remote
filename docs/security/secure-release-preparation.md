## Activation ordering and failure handling

Run the approved sealed runner in its own systemd unit outside the gateway, with
adequate timeout; do not use a gateway child process or the heavy-test unit for a
production watcher. No unit has been created or armed by this task.

1. Acquire the shared `/root/.local/state/codex-remote/deployment.lock`, then
   validate seal/evidence/readiness/dependencies and immutable baselines.
2. Call the sealed OLD authenticated watcher with `--check` twice, five seconds
   apart. Require full ALL-thread coverage, idle, and zero pending; unknown/error/
   pagination fail closed. The outer wait ceiling is twelve hours, but the bound one-hour execution-readiness
   deadline normally aborts sooner; no timeout grants authority.
3. Private backups (no owner key exists); put admin into no-store 503 and previews into parked HTTPS.
   Old readiness uses direct loopback and remains available. Recheck all baselines,
   dependencies and a third ALL-idle/zero-pending immediately before copy.
4. Guarded source fast-forward + push to exact SOURCE; keep a durable transition
   journal. Then copy assets without deleting old hashes. Atomically rename each allowlisted
   backend file and verify the complete backend including excluded files/Hours.
5. Activate exact staged dependencies and merge only six nonsecret env settings
   while preserving login secrets/workspaces/root/fullAccess. Mandatory encryption.
6. Run the sealed OLD watcher with the private original env. It does its own dual
   ALL-idle check and exactly one cutover call through its invocation-local sealed
   `runner/cutover-bin/systemctl`. Only `restart codex-remote.service` is accepted.
   The adapter uses absolute `/usr/bin/systemctl`: stop, prove old PID/cgroup/listener
   gone, init absent key, fsync identity, recheck, start exact required backend.
   Pre-key service policy must be simple/control-group/SendSIGKILL with no activation
   triggers. Never call the new encrypted adapter on the old runtime. The runner
   monitors drift and stops only its owned watcher on failure. The adapter also
   checks parent lifetime/phase/shared-lock ownership before each new effect.
7. Prove a fresh actual PID/cwd/entry command and backend hashes, then use the new
   encrypted maintenance adapter. Activate reviewed Workboard, publish index last,
   enable isolated ingress, and verify full local/public bodies.
8. Postverify encrypted proof, cookie-only legacy rejection, Files/Services/Hours
   read-only APIs, decrypted stream first record, Workboard headers, excluded modules,
   old assets and Hours generator/template. Revocation/preview ticket mutations
   remain exact-app isolated-fixture evidence: no production model/pause/logout or
   ticket creation is used as a test. If actual live ticket/revocation mutation is
   required, obtain a specifically scoped later verification plan.
9. Fsync an immutable `postverify.json` (PID/time/seal/module hashes/proof), atomically
   rename and fsync its directory **before** bookkeeping. Every later phase marker
   references this receipt. Then update Services and a checked-revision Vault note,
   with separate `services.json` / `vault.json` status files: pending, dispatching
   with unknown outcome, confirmed (Vault also records a non-applied 409). A failed bookkeeping step retains actual publication
   evidence and a failed phase; it does not masquerade as an unperformed rollout.

Every live destination (Nginx/config/env/drop-in/Workboard/assets/backend/dependency
pointer) is checked at the write against exact bytes, mode/owner, inode/device,
mtime or sealed absence, and parent identity. After an owned write, later checks
require that installed version. Full Nginx and Workboard drop-in inventories are
checked between writes and before test/reload/restart. The lock is cooperative:
other deployment tools/operators must honor it; these checks are not atomic CAS
against malicious root or a concurrent writer ignoring the lock. Remote Git has
ordinary nonforce push protection, not a distributed transaction with local Git.
After SIGKILL the shared lock remains for operator inspection; never infer safe
reclaim from PID alone. Inspect immutable proof, per-service unknown mutation
status and source journal before any manual release of the lock/new release.

File replacement is atomic per file, **not** a cross-file transaction. The gated
old process retains its loaded modules until the watcher restarts it. Partial
copies/restart failures retain `attempt.json` phase and installed-file list. There
is no retry, automatic downgrade, DB restore, old same-origin proxy, or plaintext
recovery mode. Keep public ingress gated on failure and have the leader review
exact state before a new candidate/release. A failure after reopening ingress
needs explicit containment using the sealed maintenance/parked configs; the runner
does not blindly undo a potentially concurrent operator change.
